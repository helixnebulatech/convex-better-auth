The component aims to behave exactly like Better Auth with a database adapter.
This page lists where that needs care, and the few places where behaviour is
inherited from Better Auth rather than changed by the component.

## How the component decides

When a behaviour can be implemented in more than one way, the component does
what Better Auth core or its official plugins do in the same situation. Where
Convex needs something Better Auth doesn't have, such as handing a session to an
app on another domain, it follows the closest official plugin. It may be
stricter than Better Auth, never looser, and each such case is listed on this
page with the Better Auth behaviour it's based on.

## Cross domain sessions

With the [cross domain plugin](/framework-guides/react), your app and your
Convex site are on different domains, so the session is handed to the app with a
one-time token in the `?ott=` query parameter. `ConvexBetterAuthProvider`
redeems it automatically.

- **OAuth** sign-in and account linking are tied to the browser that started
  them, as Better Auth does with its state cookie. `crossDomainClient` starts
  the redirect through your Convex site, which sets that cookie, and the
  one-time token from an OAuth sign-in can only be redeemed by the browser that
  started the flow. A sign-in started in one browser can't be finished in
  another.
- **Magic links** aren't tied to a browser, in Better Auth or here: whoever
  opens the link is signed in. Their one-time token can be redeemed from any
  browser for 3 minutes. This means that someone can request a magic link for
  their own account and send it to you, and opening it signs you in to their
  account. That's the same with Better Auth's magic links, so treat sign-in
  links you didn't request with suspicion.
- Starting OAuth requires a request from your app's origin, as in Better Auth,
  so a referrer policy such as `no-referrer` makes sign-in fail with
  `missing_or_null_origin`. See
  [Referrer policy](/framework-guides/react#referrer-policy).
- One-time tokens are only handed to the apps listed below. Callback URLs on
  other origins are redirected to without a session, and the plugin logs a
  warning with the two origins.
- The one-time tokens have their own endpoint and storage, separate from Better
  Auth's `oneTimeToken` plugin, so the two can be used together and neither can
  redeem the other's tokens.
- `crossDomainClient` keeps the session cookie in `localStorage` by default, so
  any XSS in your app can read it. Use the `storage` option to store it
  elsewhere.

### Who receives a session

Better Auth keeps the session in a cookie of the auth server. Its official
plugins hand it to another place only in these cases, and the cross domain
plugin follows the same rules:

| Flow                 | Better Auth                                                                                                                                                                                                                 | Cross domain plugin                                                                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| OAuth from a web app | `oauth-popup` and `oauth-proxy` hand it back to the trusted origin that started the flow, in the browser that started it                                                                                                    | Handed back to the origin that started the flow, if it's `siteUrl` or an exact entry of `trustedOrigins`, and only redeemable by the browser that started it |
| Magic link           | Core keeps it on the auth server. `expo` hands it only to the app's own scheme, never to another web origin, since anyone can request a link with any callback URL                                                          | Only handed to `siteUrl`, your app, as `expo` does with the app's scheme                                                                                     |
| Email verification   | With `autoSignInAfterVerification`, core signs in whoever opens the link. Since 1.7.16, confirming an email change only refreshes a session the browser already has. `expo` hands that session only to the app's own scheme | Only handed to `siteUrl`, like a magic link                                                                                                                  |
| Native app           | `expo` hands it to a trusted custom scheme such as `myapp://`                                                                                                                                                               | Left to the `expo` plugin                                                                                                                                    |

Two differences make the plugin stricter than Better Auth:

- Wildcard entries such as `https://*.vercel.app` can't start an OAuth flow.
  `oauth-popup` accepts them, but they also match sites anyone can deploy, which
  would receive the session of a user who signs in from them.
- An OAuth callback URL on another origin than the one that started the flow
  gets no session, even if that origin is trusted. Better Auth's `oauth-popup`
  always hands the session to the page that opened the popup, whatever the
  callback URL.

## Forwarded host headers

Without Convex, Better Auth learns the app's origin from the request: from the
`x-forwarded-host` and `x-forwarded-proto` headers your hosting platform's proxy
sets when `advanced.trustedProxyHeaders` is enabled, and otherwise from the
`Host` header and the request URL. A dynamic `baseURL` checks that host against
`allowedHosts`, wildcards included, and without a `baseURL` Better Auth uses the
request URL. With Convex, the request goes through a second proxy, Convex's
edge, which has its own `x-forwarded-*`. So the framework handlers
(`convexBetterAuthNextJs`, `convexBetterAuthReactStart`) and the server helpers
that fetch the Convex token send the app's host and protocol in
`x-better-auth-forwarded-host` and `x-better-auth-forwarded-proto` instead, and
don't send `x-forwarded-*`. Like any proxy, they set these headers from the
request URL or the platform's headers, and replace values a client sent.

Your Convex site URL is publicly reachable, so any client can set these headers,
`x-forwarded-*` and, on a self-hosted backend, `Host` too. So the component, as
the proxy in front of Better Auth, decides the origin of every request and sets
the request URL, `Host`, `x-forwarded-host` and `x-forwarded-proto` all to it,
whatever `trustedProxyHeaders` says. It picks the first of:

1. The app's origin from `x-better-auth-forwarded-*`, or else the
   `x-forwarded-*` the request arrived with, when together they form an origin
   listed exactly in `trustedOrigins`, `BETTER_AUTH_TRUSTED_ORIGINS` or the
   `allowedHosts` and `fallback` of a dynamic `baseURL`.
2. The request's own origin, when it's listed exactly, such as a custom domain
   for your Convex site.
3. `CONVEX_SITE_URL`, which only the deployment sets. On Convex's cloud this is
   the origin requests arrive at anyway, so nothing needs configuring. Convex
   always sets it; if it's missing, the request's own origin is used.

The `x-better-auth-forwarded-*` headers are removed before Better Auth sees the
request. Origins are compared as protocol and host, so an origin listed only
with `https://` is never used over `http://`, and a host with a path, user info
or an explicit default port doesn't count.

This is stricter than Better Auth in two ways:

- Wildcard entries such as `*.vercel.app` in `trustedOrigins` or `allowedHosts`
  don't count. Better Auth accepts them for a dynamic `baseURL`, but anyone can
  deploy to a shared platform domain, and the base URL decides where links in
  emails such as password reset and verification links point. A request from an
  app on a wildcard host gets the `fallback` origin.
- A host only reaches Better Auth through the component, so a client can't pick
  one Better Auth would accept but you didn't list exactly. The worst a caller
  can do is pick another of the origins you listed exactly.
- If `trustedOrigins` is a function, the component calls it with the request as
  if it had arrived at `CONVEX_SITE_URL`, so a function that trusts the origin
  of the request's own host, as some preview setups do, can't make a client's
  host trusted. Better Auth calls it with the request it receives. Don't return
  origins read from other request headers, such as `Origin`: a client sets
  those.

Better Auth only uses the app's origin when it takes the base URL from the
request: with a dynamic `baseURL`, or without a `baseURL`. Then links in emails,
OAuth callback URLs and, with `crossSubDomainCookies`, the cookie domain follow
the app's origin. With a static `baseURL` they always use that URL.

### Self-hosted Convex

A self-hosted Convex backend, tested with the local backend that `convex dev`
runs, passes the `Host` and `x-forwarded-*` headers a client sends to your HTTP
actions and builds the request URL from them. The component replaces all of them
as described above, so a self-hosted deployment needs no reverse proxy for this.
Before 0.13.9, it only replaced `x-forwarded-*`, and a dynamic `baseURL` with a
wildcard in `allowedHosts` took a client's `Host` header
([GHSA-9qq3-v9g3-cxhw](https://github.com/convex/better-auth/security/advisories/GHSA-9qq3-v9g3-cxhw)).

Make sure `CONVEX_SITE_URL` is your backend's public site URL (set from
`CONVEX_SITE_ORIGIN` on a self-hosted backend), since it's the origin used when
a request's own isn't listed.

## Database adapter

Better Auth leaves some guarantees to the database. The component provides them
the way Better Auth's SQL adapters (Drizzle, Prisma, Kysely) get them from the
database:

- **Ids chosen by Better Auth.** Some flows create a row with an id Better Auth
  derives from a value and rely on the primary key to reject a second one:
  reserving a verification value (magic link, email OTP, SIWE) and the OAuth
  provider's `private_key_jwt` replay check. Convex picks `_id` itself, so the
  component keeps the chosen id in an indexed `customId` field and rejects a
  duplicate in the same mutation. This works with the default ids and with
  `advanced.database.generateId: "uuid"`. With `"serial"`, Better Auth itself
  doesn't enforce these checks and logs a warning, on any database.
- **Unique fields.** Better Auth relies on the database to reject a duplicate
  `email`, `username` or other unique field. The component checks it in the same
  mutation as the write. A null or unset value never conflicts, as NULL in a
  unique column in SQL, so any number of users can have no `username`.
- **Account keys.** Two accounts can't share a `providerId` and `accountId`.
  This is stricter than Better Auth's SQL schema, which has no constraint for
  them, but Better Auth's internal adapter (`findAccountByKey`,
  `findAccountOwnerByKey`) throws `Multiple accounts match` when two accounts
  do, so two requests racing to link the same provider account would break
  sign-in with it. The component rejects the second account in the same
  mutation as the write, on create and on update.
- **Sorting.** Better Auth's adapters always honour `sortBy`. Convex reads rows
  in index order, so when no index ends in the sort field, the component reads
  every row that matches the query and sorts them, as SQL does with `ORDER BY`
  and no index. Nulls and unset values come first, as in a Convex index. On a
  large table this can hit Convex's read limit, which fails the query instead of
  returning the wrong rows. Add an index ending in the sort field for lists you
  sort often. A range (`lt`, `gt`...) on another field also sorts this way, as
  an index scan with a range returns rows in the order of the ranged field.
- **Updating many rows.** `updateMany` updates every row that matches when it
  runs once, as SQL's `UPDATE ... WHERE`. The component collects the matching
  ids first and updates them in chunks of 200, applying the `where` again in
  each chunk, so an update that moves a row in the index the `where` reads
  doesn't update it twice. From an action, each chunk is its own transaction.
- **Atomic counters.** Better Auth's `incrementOne` (rate limits, two factor
  lockouts, team seats) and `consumeOne` (verification values, one-time tokens)
  read, check and write one row in a single mutation, which Convex runs as a
  transaction, as Kysely does in one `UPDATE ... WHERE` or `DELETE ... WHERE`.
  An unset or null counter counts as 0, as in Better Auth's memory adapter and
  its atomic fallback.
- **Comparisons with `undefined`.** A `where` clause whose value is `undefined`
  matches no row, as Better Auth's SQL adapters bind it as NULL and a
  comparison with NULL is never true. It doesn't match rows where the field is
  null, as `eq null` does.

## Adapter calls without a where clause

Better Auth always passes a `where` clause when it deletes or updates rows. If
you call the adapter or the component's adapter functions yourself, always pass
one too. With an empty `where`:

| Call                                     | Effect                            |
| ---------------------------------------- | --------------------------------- |
| Adapter `delete`                         | Deletes the first document        |
| Adapter `consumeOne`                     | Deletes and returns the first one |
| Adapter `incrementOne`                   | Updates and returns the first one |
| Adapter `update`                         | Does nothing and returns `null`   |
| Adapter `deleteMany` / `updateMany`      | Deletes / updates every document  |
| Component `adapter.deleteOne` (no where) | Deletes the first document        |
| Component `adapter.updateOne` (no where) | Updates the first document        |

Better Auth's own adapters don't agree on this either. With Postgres, Better
Auth runs `delete from "session" where 1 = 1` and deletes every row.
`consumeOne` and `incrementOne` take the first row as Better Auth's Kysely and
memory adapters and its atomic fallback do; upstream returns `null` instead.

## Tokens and revocation

The JWT Convex uses holds the user's fields, except `id`, `image` and fields
with `returned: false`. `ctx.auth.getUserIdentity()` checks the JWT, not the
session, so it stays valid after sign-out or a ban until the JWT expires (15
minutes by default). Use `authComponent.getAuthUser` or `safeGetAuthUser` when
the session must be checked. With [JWT caching](/experimental),
`isAuthenticated()` always checks the session with the server.

The Convex JWT is only signed where Better Auth's `jwt` plugin signs its own: by
`/convex/token`, which requires a session, and after `/get-session` returns one,
when it's also stored in the `convex_jwt` cookie. It's never signed on sign-in,
so a plugin that holds a sign-in back, such as `twoFactor` waiting for the
second factor, can't leave a JWT behind whatever the plugin order. A request
that starts a new session, sign-out, and any response that expires the session
cookie clear the `convex_jwt` cookie, the way Better Auth's
`deleteSessionCookie` clears the cookies derived from the session
(`session_data`, `account_data`). So when `twoFactor` holds a sign-in, which
expires the session cookie, the JWT of a user who was signed in before in the
same browser is cleared too, whatever the plugin order. With the cross domain
plugin, every cookie of the response, including these, reaches the client in
`Set-Better-Auth-Cookie`, also those set by plugins listed after it.

## Users returned to the client

Better Auth runs every user it sends to a client through `parseUserOutput`,
which leaves out fields marked `returned: false`. The public query from
`authComponent.clientApi(createAuth)` does the same with your options. Without
`createAuth` the component can't know which fields your options hide, so it's
stricter and only returns the core Better Auth user fields and the Convex
document fields. `getAuthUser` and `safeGetAuthUser` return the whole document,
as they're meant for server code.

## Verbose logs

`verbose: true` logs request and response headers with cookies, tokens and API
keys redacted, and the query string of `location` and `referer` removed. It no
longer enables Better Auth's adapter debug logs, which print whole database
rows, including session tokens, password hashes and verification values. Those
have their own `debugLogs` option, off by default, which takes the same values
as the `debugLogs` of Better Auth's adapters. Better Auth doesn't redact them
either, so only enable either option while debugging, and `debugLogs` never in
production.

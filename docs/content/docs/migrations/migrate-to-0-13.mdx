## Breaking changes

<div className="fd-steps">

  <div className="fd-step">

### Use `signIn.social` for Generic OAuth providers

Better Auth 1.7 registers each Generic OAuth provider as a social provider.
Remove `genericOAuthClient()` from your auth client, and use `signIn.social`
instead of `signIn.oauth2`.

```ts
export const authClient = createAuthClient({
  plugins: [
    genericOAuthClient(), // [!code --]
    convexClient(),
  ],
});

await authClient.signIn.oauth2({ providerId: "slack" }); // [!code --]
await authClient.signIn.social({ provider: "slack" }); // [!code ++]
```

The callback URL changes from `/api/auth/oauth2/callback/<providerId>` to
`/api/auth/callback/<providerId>`. Update the redirect URL in the settings of
each OAuth provider.

  </div>

  <div className="fd-step">

### OIDC Provider tables are removed from the default schema

Better Auth 1.7 removes the deprecated `oidcProvider` plugin. The default
component schema no longer has the `oauthApplication`, `oauthAccessToken` and
`oauthConsent` tables.

If your app does not use the OIDC Provider plugin, you do not have to do
anything.

If your app uses it, move to
[`@better-auth/oauth-provider`](https://www.better-auth.com/docs/plugins/oauth-provider)
with [Local Install](/local-install). The deploy does not delete documents that
are in the old tables.

  </div>

  <div className="fd-step">

### Move `experimental.joins` to `advanced.database.joins`

If you set `experimental: { joins: true }`, change it to
`advanced: { database: { joins: true } }`. The Convex adapter does not support
joins yet, so it continues to set this option to `false`.

  </div>

  <div className="fd-step">

### Review breaking changes in Better Auth 1.7

Be sure to review the
[Better Auth 1.7 release post](https://better-auth.com/blog/1-7) for other
breaking changes that can have an effect on your app. For example,
`twoFactor.enable` now returns a `method` field. Check that `method` is `"totp"`
before you read `totpURI` and `backupCodes`.

  </div>

</div>

## Upgrading to 0.13.2

0.13.2 adds indexes to the component schema. Apps using the default install get
them on their next deploy. Apps using [Local Install](/local-install) need to
regenerate their schema and deploy to get them:

- `rateLimit.lastRequest`, used when Better Auth deletes expired rate limit
  rows.
- Indexes for the unique constraints Better Auth declares at the table level,
  such as `deviceCode` and `userCode` for the device authorization plugin.

```npm
cd convex/betterAuth
npx auth generate
```

Without the new indexes everything keeps working, but these queries scan the
whole table, and unique checks without an index log a warning asking you to
regenerate the schema.

## Upgrading to 0.13.3

0.13.3 includes security fixes. See the [security notes](/security) for how the
component behaves now.

### Cross domain apps

With the cross domain plugin, OAuth sign-in now goes through your Convex site
before the provider, so it's tied to the browser that started it, as it is with
Better Auth on a single domain.

- Deploy your Convex backend and your frontend together. An old client can't
  complete an OAuth sign-in against the new server, and the other way round.
  Users with the app already open need to reload it before signing in with an
  OAuth provider. Email, magic link, OTP and existing sessions aren't affected.
- If you call `signIn.social` or `linkSocial` with `disableRedirect: true`,
  start the redirect with `authClient.startOAuthRedirect(data.url)` instead of
  opening the URL yourself.
- The session is only handed to your app at `siteUrl`. Callback URLs on other
  origins, even trusted ones, are redirected to without a session.
- If your app sets a referrer policy such as `no-referrer` (the default of
  `helmet`), OAuth sign-in fails with `missing_or_null_origin`. See
  [Referrer policy](/framework-guides/react#referrer-policy) for the fix and the
  `setReferrerPolicy` option.

### JWT caching

If you use `jwtCache`, `isAuthenticated()` now checks the session with the
server on every call, like Better Auth's `getSession`. Other server helpers
still reuse the cached JWT, after verifying its signature. If the
`convexSiteUrl` you pass differs from `CONVEX_SITE_URL` in your deployment, set
`jwtCache.issuer` so the cached JWT can be verified.

### Queries on null fields

`lt`, `lte`, `gt`, `gte`, `ne` and `not_in` where clauses no longer match
documents where the field is null or unset, as with Better Auth's SQL adapters.
Check your own queries through the component adapter if they relied on that.

## Upgrading to 0.13.4

### Better Auth returns dates as `Date` objects

The adapter now hands date fields (`createdAt`, `updatedAt`, `expiresAt`, and
any additional field of type `date`) to Better Auth as `Date` objects instead
of epoch milliseconds. This is what Better Auth's types have always said, and
what Better Auth expects: with numbers, the session cookie cache never
validated, and code paths that call `.getTime()` on a date threw. If you
disabled `session.cookieCache` because of `Cookie cache payload failed schema
validation` warnings, you can turn it back on.

Dates are still stored as numbers in Convex, so no data migration is needed,
and these keep returning numbers:

- `authComponent.getAuthUser()`, `safeGetAuthUser()` and `getAnyUserById()`
- triggers
- the claims of the Convex JWT, so `ctx.auth.getUserIdentity()` is unchanged
- `auth.api.rotateKeys()` and `auth.api.getLatestJwks()`

What changes is the result of `auth.api.*` calls and of the adapter. Convex
functions can't return `Date` objects, nor pass them to `ctx.runMutation`,
`ctx.runQuery` or the scheduler. If a function returns a Better Auth result
that holds dates, convert them first, or it fails with
`Date "…" is not a supported Convex type`:

```ts
export const getCurrentSession = query({
  args: {},
  handler: async (ctx) => {
    const { auth, headers } = await authComponent.getAuth(createAuth, ctx);
    const session = await auth.api.getSession({ headers });
    if (!session) {
      return null;
    }
    return session.session; // [!code --]
    return { // [!code ++]
      ...session.session, // [!code ++]
      createdAt: session.session.createdAt.getTime(), // [!code ++]
      updatedAt: session.session.updatedAt.getTime(), // [!code ++]
      expiresAt: session.session.expiresAt.getTime(), // [!code ++]
    }; // [!code ++]
  },
});
```

The same applies to Better Auth's `databaseHooks` and plugin hooks: the rows
they receive now hold `Date` objects.

Responses of the Better Auth HTTP endpoints, such as `/get-session`, now carry
dates as ISO strings, as with any other Better Auth adapter, instead of
numbers. Clients that read them as numbers should parse them with
`new Date(value)`.

## Upgrading to 0.13.5

0.13.5 adds indexes for Better Auth lookups that had none. Apps using the
default install get them on their next deploy. Apps using
[Local Install](/local-install) need to regenerate their schema and deploy:

```npm
cd convex/betterAuth
npx auth generate
```

### Credential account index

The new `accountId_providerId_userId` index on the `account` table is for the
lookup Better Auth 1.7 runs on a user's credential account when resetting,
changing or setting a password. Earlier 0.13 releases had no index for it, so
the lookup read at most 200 rows of the `account` table and missed accounts
beyond them. When that happened, password reset and set password created a
second credential account instead of updating the existing one. Sign-in kept
checking the password of the first account, so the user got a 401 with their
new password. With fewer than 200 accounts, as in most development
deployments, the lookup worked and only logged a `Querying without an index`
warning.

If your app ran an earlier 0.13 release with more than 200 accounts, check for
users with more than one account where `providerId` is `credential`. The newest
of these rows holds the password the user set last. Delete the older rows so
sign-in uses the newest one, and ask the user to reset their password again if
you aren't sure which one they expect.

### Lookups without an index

Single row lookups (`findOne`, `update`, `delete`) without an index now keep
reading the table until they find a matching row or reach its end. Earlier 0.13
releases stopped after the first 200 rows and reported the row as missing, which
is how the credential account lookup above created duplicates. A lookup without
an index is still slow and logs a `Querying without an index` warning, and on a
large table it can fail with Convex's read limit instead of returning a wrong
result. Add the index the warning asks for.

### Other new indexes

- `session.userId_expiresAt`, for listing a user's active sessions
  (`/list-sessions` and the anonymous plugin). Without it, each call read the
  whole `session` table.
- `twoFactor.secret`.

Schema generation now creates an index for every field Better Auth marks with
`index: true`, as the Drizzle and Prisma generators do. Before, these fields
had no index, so lookups on them could miss rows past the first 200 of the
table, as with the credential account. This affects Local Install apps using:

- the API key plugin: `apikey.key`, checked on every request authenticated
  with an API key, plus `referenceId` and `configId`.
- the passkey plugin: `passkey.credentialID`, used for passkey sign-in.
- the OAuth provider plugin: `authorizationCodeId` in `oauthAccessToken` and
  `oauthRefreshToken`.

Local Install apps also get indexes for lookups by these plugins:

- Organization: `member.organizationId_userId`, `teamMember.teamId_userId`,
  `invitation.email_organizationId_status_expiresAt`,
  `invitation.organizationId_status` and `organizationRole.organizationId_role`.
- SIWE: `walletAddress.address_chainId`.
- SSO: `ssoProvider.domain`.
- OAuth provider: `oauthConsent.clientId_referenceId_userId`,
  `oauthClient.referenceId` and `oauthRefreshToken.clientId_userId`.
- API key: `apikey.expiresAt`.
- Stripe: `stripeCustomerId` on `user` and `organization`, and
  `subscription.referenceId_status`, `subscription.stripeSubscriptionId` and
  `subscription.stripeCustomerId`.
- SCIM: compound indexes on `scimGroupMember`, `scimManagedConnectionEvent`,
  `scimManagedCredential`, `scimProjectionGrant` and `scimUser`.

Indexes on fields a table doesn't have, such as the Stripe fields when Stripe
isn't used, are skipped.

Schema generation now keeps the field order of compound indexes. It used to
sort them alphabetically, which put range fields such as `expiresAt` before the
equality fields and made the index unusable. If you add your own indexes, list
the fields compared with equality first, then the field compared with a range
(`lt`, `gt`...), then the field you sort by.

## Upgrading to 0.13.6

0.13.6 is tested with Better Auth 1.7.13:

```npm
npm install better-auth@~1.7.13
```

Apps using the default install get the schema change below on their next deploy.
Apps using [Local Install](/local-install) need to regenerate their schema and
deploy:

```npm
cd convex/betterAuth
npx auth generate
```

### Ids chosen by Better Auth

Since Better Auth 1.7.8, some flows create a row with an id Better Auth derives
from a value, and rely on the database rejecting a second row with the same id.
Convex picks `_id` itself, so earlier 0.13 releases rejected these rows and the
flows failed:

- Magic link and email OTP sign-in for a user whose email isn't verified yet,
  for example someone who signed up with a password and never verified the
  email. Better Auth removes the accounts and sessions the user had before
  proving the email, and the request failed with a 500.
- SIWE sign-in that claims an email.
- `private_key_jwt` client authentication in the OAuth provider plugin.

The `verification` and `oauthClientAssertion` tables now have an optional
`customId` field with an index. The component stores the chosen id there and
rejects a second row with the same id, like a primary key. Until a Local Install
app regenerates its schema, these flows keep failing, with an error that asks to
regenerate the schema.

## Upgrading to 0.13.7

0.13.7 includes security fixes. See the [security notes](/security) for how the
component behaves now.

### Convex JWT cookie

The Convex JWT is no longer signed on sign-in, only by `/convex/token` and after
`/get-session` returns a session, as Better Auth's `jwt` plugin does. This fixes
a two-factor bypass when `convex()` was listed before `twoFactor()`. After a
sign-in, the `convex_jwt` cookie is set by the first `/get-session` call, which
the client makes right away; server-side helpers without the cookie fetch the
token from `/convex/token`, as before. Requests that start a new session clear
the cookie.

The Convex JWT is now always signed with the algorithm in your Convex auth
config. `rotateKeys` and `getLatestJwks` only touch those keys, so they no
longer delete or export keys of Better Auth's `jwt` plugin.

### Forwarded headers

The component now sets `x-forwarded-host` and `x-forwarded-proto` itself before
calling Better Auth: only for an origin listed exactly in your trusted origins,
and otherwise it removes them. On Convex's cloud nothing changes for apps. On
self-hosted Convex, see [Self-hosted Convex](/security#self-hosted-convex). If
your app uses `advanced.trustedProxyHeaders` with a wildcard in `allowedHosts`,
list the hosts exactly.

### TanStack Start `isAuthenticated`

`convexBetterAuthReactStart` now returns `isAuthenticated()`, which checks the
session with the server. With `jwtCache`, `getToken()` can return a cached JWT
that stays valid after the session ends, so use `isAuthenticated()` where the
session must be checked.

### Database adapter

These now behave as with Better Auth's SQL adapters:

- Any number of rows can have a null unique field, such as users without a
  `username`.
- `sortBy` is honoured when no index ends in the sort field. The component reads
  the matching rows and sorts them, so add an index for lists you sort often on
  large tables.
- Ids chosen by Better Auth are kept with
  `advanced.database.generateId: "uuid"`.
- Renamed fields work in `sortBy` and `select`.

### OAuth sign-in from other apps

With the cross domain plugin, an OAuth sign-in can now start from any app listed
exactly in `trustedOrigins`, not only from `siteUrl`, and the session is handed
back to the app that started it. This is what Better Auth's `oauth-popup` plugin
does. Wildcard entries such as `https://*.vercel.app` still can't start a flow,
and magic links still only hand the session to `siteUrl`. See
[Who receives a session](/security#who-receives-a-session).

Relative `callbackURL`, `newUserCallbackURL` and `errorCallbackURL` values of an
OAuth sign-in now resolve against the app that started it. Apps that only run at
`siteUrl` see no change.

### SCIM list indexes

Apps using the SCIM plugin with [Local Install](/local-install) get
`connectionId_orderKey` indexes on `scimUser` and `scimGroup`, for the `/Users`
and `/Groups` lists. Regenerate the schema and deploy:

```npm
cd convex/betterAuth
npx auth generate
```

### Sign-in after email verification

With the cross domain plugin and `autoSignInAfterVerification`, opening the
verification link now signs the user in to the app at `siteUrl`, like a magic
link. The same applies when confirming an email change. Before, Better Auth
created the session but the app never received it.

### Using the plugins with other Better Auth plugins

The cross domain and Convex plugins registered some endpoints under the same
keys as Better Auth's `oneTimeToken`, `jwt` and `oauthProvider` plugins, so
using them together removed endpoints of one or the other. They now use keys of
their own. If you called these endpoints on the server, rename the calls:

| Before                                         | After                                      |
| ---------------------------------------------- | ------------------------------------------ |
| `auth.api.getToken()` (Convex)                 | `auth.api.getConvexToken()`                |
| `auth.api.getJwks()` (Convex)                  | `auth.api.getConvexJwks()`                 |
| `auth.api.getOpenIdConfig()`                   | `auth.api.getConvexOpenIdConfig()`         |
| `auth.api.verifyOneTimeToken()` (cross domain) | `auth.api.crossDomainVerifyOneTimeToken()` |
| `auth.api.startOAuth()`                        | `auth.api.crossDomainOAuthStart()`         |

The paths and the clients don't change. A cross domain sign-in that is between
the redirect and the token exchange during the upgrade fails, and the user has
to sign in again.
